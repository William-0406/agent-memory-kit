# Codex / Kimi 接力规则

> 目标：上午在 Codex 聊过的事，下午打开 Kimi 能立即接上；反过来也一样。
> 接力记录是助手摘要，不是 {owner} 原话，不能拿去训练 `语气档案.md`。

## 一、共同原则

- 本目录是双方唯一共享的事实来源，不依赖各自的内置记忆碰运气。
- 每个助手写自己的接力文件，不能覆盖另一个助手的文件。
- 不等“对话结束”才交接。真要写的时候及时写，避免关掉窗口后丢失。
- 闲聊、临时问答和随时能重新查到的公开信息不用记录。
- 交接只解决短期连续性；稳定事实、决定、承诺和知识仍写进原来的长期文件。
- 🔴 **[2026-11-09] 开场不靠接力找状态。** 状态来源是 `待办与承诺.md` 和 `工作/<项目>.md` 的「📍 当前状态」头；接力只记「上一轮在同一话题上停在哪」。找不到接力不是异常。

## 二、开始时怎么读

**开场怎么读的唯一清单在 `AGENTS.md`「每次开始任务」（Codex / Kimi 共用）。本文件不再维护第二份。**

（[2026-08-27 订正] 此处原有一份 4 步清单，写着「读 `交接/` 下最新 3 份」——`CLAUDE.md` / `AGENTS.md` 08-14 已改成**最新 1 份**，且开场还要求先跑记忆网关、读 `自检规则.md`，本清单一条都没跟上。两份清单并存 13 天，每次开场都在读一份自相矛盾的指令。这正是 08-03「`CLAUDE.md` / `AGENTS.md` 分叉五天」的同族错误：**一份内容一个家。**）

## 三、什么时候写

> 🔴 **[2026-11-09 {owner} 拍板：改成事件触发，不再每轮必写。]** 改版理由、数据与代价见本文件末「七、改版记录」。

**默认不写，只有三种情况写：**

1. **产生了要跨会话接着做的东西**（未闭环任务、明确下一步、需他侧接手）。
2. **{owner} 说「先这样/明天继续」，或要换窗口、切助手。**
3. **改了记忆库的结构或规则本身。**

「完成了任务」不单独构成理由——产出进 `工作/<项目>.md` 或 `待办与承诺.md`；一次性评估、查证结论、闲聊都不写。

**判断句：下一轮有人真的需要读到吗？说不出是谁、在什么场景需要，就别写。**

## 四、文件规则

- 路径：`交接/YYYY-MM/`

🔴 **「规则计分」一节是 2026-08-18 加的，不能省。**
四元组来自 `自检规则.md` 维护节：**触发机会 → 是否命中 → 谁发现（我自己 / git 钩子 / {owner}）→ 是否在提交前拦下**。
新写表格的状态列统一用「是 / 否 / 部分命中 / 本轮无触发」，解释放在状态词后；规则名优先写固定编号。部分命中单独列为未确认，不算成功。若存在 {owner} 发现的未命中，在本接力写 `回归案例：<id>`，对应案例须已在 `记忆网关/回归案例.jsonl`；提交检查共用汇总解析器验证关联。历史接力原文保留。[源:{owner} 2026-09-20 授权架构修复][源:scripts/rule-scores.mjs]
**本轮一条都没触发也要写「本轮无触发」**——如果「没触发」和「忘了记」在文件里长得一样，这个计分就是假的。
`scripts/memory-check.mjs` 会在提交时检查本次变更的接力：缺节、空表且未写无触发、{owner} 纠错缺回归关联会拦下提交；历史自由格式无法判读时提醒。**它检查格式与关联，不能证明计分内容真实。**

🆕 **[2026-10-28] 两处补充（来源：Claude Code 团队 code review 流程）**：

- **「误报」列只在审查类任务填**（页面/UI 自查、代码复核、文档核对、检索验收）；日常问答不填。填的数字必须与 `记忆网关/审查台账.jsonl` 当日那一行一致，否则台账和接力会分叉。审查类任务**没误报就写 0**，不能留空——空白和「没记」在文件里长得一样，计分就假了。
- **验证结论只对当次改动有效**：写了「已验证」，之后任何人再改一行，这个结论即失效。接力里若引用旧验证，必须写明验证的是哪个版本/提交，不许拿旧结论当新证据。

没有内容的章节可以删除。摘要要短，但必须保留决定理由、未解决问题和相关文件。

## 六、沉淀到长期记忆

接力完成后，再判断是否需要同步到：

- 稳定事实 → `我是谁.md`
- 决定和排除理由 → `决策记录.md`
- 未闭环事项 → `待办与承诺.md`
- 项目进展 → `工作/<项目>.md`
- 日常事件 → `生活/日志/<年-月>.md`
- 有长期价值的知识 → `知识/<主题>.md`
- 对 {owner} 的观察、助手的立场、稳定的局限或不确定 → `助手侧记.md`
- 助手出的错（经过与归因）→ `纠错记录.md`；可执行的拦法 → `自检规则.md`

不要把同一句话机械复制到所有文件。

## 七、改版记录

### 2026-11-09 · 接力从「每轮必写」改为「事件触发」

**触发**：如果只有一个助手在干活，接力存在的原始目的（交接给另一个助手）就消失了，剩下的是纯开销。判断方式：**规则存在的原始目的消失时，该怀疑规则本身，而不是照做。**

**数据**（原使用者的实测，非估计）：

- 5 个工作日写了 **26 份**接力，共 **183,872 字符**；其中一天 10 份。
- 开场只读**最新一份**的「当前状态」小节——**前面 25 份的状态小节全是死重**。
- 旧规则第一条「完成了任务、修改了文件或生成了产物」几乎每轮都命中，等于没有条件。

**代价与处置**：

- 不写接力时 `scripts/memory-check.mjs` 不会检查它（该检查只遍历本次改动涉及的接力文件），**不报错**——停写是安全的。
- 但「规则计分」「对 {owner} 的新观察」两节在没写接力的轮次就断了连续记录。趋势改用 `node scripts/rule-score-report.mjs --since <日期>` 按需汇总，**不靠每轮攒**；观察改成随时可追加进 `助手侧记.md`。
- ⚠️ **副作用**：L3 审阅的触发条件是「`交接/` 新增 ≥ 3 份或距上次 ≥ 7 天」。停写接力后「≥3 份」几乎无法触发，**实际只剩「≥7 天」在起作用**。这符合本意（审阅本就该按时间触发），但规则文字与这一现实不完全对应，知道即可。

### 2026-11-09 · 开场取最新接力改为按文件名排序

**问题**：`latestHandoff` 原来按 mtime 取「最新一份」。于是**改任何旧接力都会让它变成"最新"**，开场读到的「当前状态」会是被订正的旧接力，今天那份反被顶掉，状态直接过期。

**修法**：接力文件名本身就带 `YYYY-MM-DD_HHmm`，**按文件名排序才是真实的写作时序**。mtime 只反映"谁最后被碰过"，不反映"谁是最后写的"。已加回归测试钉死。
